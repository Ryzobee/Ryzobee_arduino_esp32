# TOUCH4 四通道触摸模块示例

[English](README.md)

根据 [mian.c](../mian.c) 中 SC92F8372/8371/8370 触控固件封装，名称 `TOUCH4` 表示四通道触摸模块，不是固件给出的商业型号。原文件保留作为协议来源。本驱动仅适用于 `SSI_MODE == UART`，不实现 I2C 模式。

## 接线与运行

安装 Ryzobee、Yoke 和 ESP32 开发板核心，无需额外第三方库。编译并烧录 `Yoke_TOUCH4.ino`。示例每 100 ms 请求触摸状态和四路原始值，每次命令最多等待 1000 ms。固件不会主动上报，必须发送请求。

| 主机 RS_PORT4 信号 | RootMaker GPIO | 模块信号 |
| --- | --- | --- |
| 第二个引脚 / SCL，主机 TX | 18 | RX |
| 第一个引脚 / SDA，主机 RX | 17 | TX |
| GND | GND | GND |

当前示例在初始化前交换 RS_PORT4 的两个端口引脚，使用 TX=GPIO18、RX=GPIO17，以测试模块串口接线方向。

按模块实际规格供电，串口信号须与 ESP32 电平兼容；不要根据 MCU 名称推断模块供电电压。波特率固定 9600，8 数据位、无校验、1 停止位。每个实例独占一个 UART；不要与 RAD60、串口控制台等共用同一 UART。`begin()` 成功表示主机串口就绪，`getVersion()` / `readData()` 成功才证明收到有效设备回复。

## 使用接口

| 接口 | 功能 |
| --- | --- |
| `begin(board.maker.useport("rs_port4"))` | 初始化并占用 RS 端口，成功返回 `YOKE_PORT_ERROR_NONE` |
| `readData()` | 同步请求并缓存四路触摸数据，成功返回 true |
| `update()` | 非阻塞接收并解析串口数据，不发送查询 |
| `getTouchMask()` / `isTouched(channel)` | 读取缓存的触摸位，逻辑通道 0～3 |
| `getRawData(channel)` | 读取缓存的 16 位原始值 |
| `hasData()` | 本次初始化后是否收到过有效数据，不代表缓存仍是最新 |
| `setEnabledChannels(mask)` | 通道使能掩码 0x00～0x0F |
| `setThresholds(data)` | 写入 8 个阈值配置字节，并由固件重新初始化触摸 |
| `reconfigure()` | 重新初始化触摸 |
| `getChannelConfig(channel, data)` | 读取一个固件配置通道的 8 个字节 |
| `setChannelConfig(channel, data)` | 写入一个固件配置通道的 8 个字节，随后调用 `reconfigure()` 应用 |
| `getVersion(&version)` | 查询 16 位固件版本，源文件为 0x1001 |
| `end()` | 释放 UART 和 RS 端口，端口数据须保持有效直到调用完成 |

读取失败保留旧缓存；只有 `readData()` 返回 true 时才使用本次读取结果。所有命令按顺序调用，不支持并发任务使用同一实例。

原始值上报顺序为 `RawData[3]`、`RawData[2]`、`RawData[0]`、`RawData[1]`，触摸掩码 bit0～bit3 分别来自 `exKeyValueFlag` 的 0x0100、0x0020、0x0001、0x0002。配置接口中的 channel 则直接索引 `TKChannelCfg[channel]`；不要假设它与上报顺序相同。阈值命令依次写入 `TKChannelCfg[0..3][6..7]`。源文件未给出配置字节语义，因此驱动保留原始字节，不推测阈值单位或参数含义；示例不覆盖默认配置。

## 串口协议

帧格式为 `AA 55 CMD LEN DATA... CRC EE`。CRC8 多项式 0x31，初值 0，无反射，无最终异或；仅计算 CMD、LEN 和 DATA。原始值及版本高字节在前。驱动拒绝长度超限、CRC 错误和帧尾错误的数据。

| 请求 → 回复 | 数据 |
| --- | --- |
| 0x21 → 0x11 | 请求带 1 个占位字节；回复 9 字节：触摸掩码及四路 16 位原始值 |
| 0x22 → 0x12 | 请求通道掩码；回复实际掩码 |
| 0x23 → 0x13 | 请求 8 字节阈值；回复 1 表示成功 |
| 0x24 → 0x14 | 请求带 1 个占位字节；回复 1 表示成功 |
| 0x25 → 0x15 | 请求配置通道索引；回复 8 字节配置 |
| 0x26 → 0x16 | 请求通道索引加 8 字节配置；回复 `1 | (channel << 4)` |
| 0x2F → 0x1F | 请求带 1 个占位字节；回复 2 字节版本 |

源固件的 `case 0x26` 缺少 `break`，可能额外发送版本帧，且连续启动发送可能覆盖尚未发完的 ACK。驱动只接受当前命令对应的回复，额外版本帧不会被当作配置 ACK；若配置应答异常，应在设备固件中修正此处发送流程。协议没有请求序号，超时后的迟到回复无法与同类新请求完全区分。

## 超时诊断

示例默认关闭原始收发跟踪，仅在通道触摸或释放时打印 `Channel N pressed/released`，显示编号为 1～4（驱动索引仍为 0～3）；持续按住不会重复打印，不持续打印原始值；持续读取失败时每 5 秒最多提示一次，首次失败立即提示。需要诊断时，在首次查询前添加 `touch.setDebugStream(&Serial)`，即可打印发送帧、收到的每个字节和通过校验的帧。只有 TX 而没有 RX 时，检查模块供电、接线、RX/TX 方向及 UART 固件模式；有 RX 但没有 valid frame 时，检查波特率、CRC 和实际协议；有 valid frame 仍超时时，对比回复命令和长度。诊断后用 `touch.setDebugStream(nullptr)` 关闭。调试输出必须使用与设备 UART 分离的串口。

## 按键式事件输出

每次成功读取后，对比新旧触摸掩码，逐通道打印按下和松开事件，例如 `Channel 1 pressed`、`Channel 1 released`。启动时已经触摸的通道在首次读取时打印按下。查询周期仍为 100 ms，并非硬件中断；通信中断期间或两次查询之间完成的变化可能无法捕获。若模块状态本身波动，仍会产生交替事件。通信恢复时保留上次有效状态进行比较，不重复报告持续按住的通道。
